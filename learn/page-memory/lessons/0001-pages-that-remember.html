1. The problem: Back threw your work away

BoxHarbor is a Next.js app. Leaving a page unmounts its React components, and their state goes with them. So you'd set filters, page to 3, open a poster, press Back, and land on page 1 with everything reset. Worse, a release table that took up to 20 seconds to fill started over from blank.

2. The helper: 42 lines, no dependencies

const PREFIX = "boxharbor:page:";

export type Saved<T> = { at: number; value: T };

export function readSession<T>(key: string, maxAgeMs: number): Saved<T> | null {
  try {
    const raw = sessionStorage.getItem(PREFIX + key);
    if (!raw) return null;
    const saved = JSON.parse(raw) as Saved<T>;
    if (typeof saved?.at !== "number" || saved.value === undefined) return null;
    if (Date.now() - saved.at > maxAgeMs) return null;
    return saved;
  } catch {
    return null;
  }
}

export function writeSession<T>(key: string, value: T): void {
  try {
    sessionStorage.setItem(PREFIX + key, JSON.stringify({ at: Date.now(), value }));
  } catch {
    // Storage full or blocked (private window): the next visit starts fresh.
  }
}

/** "just now", "4 min ago", "2 hr ago". */
export function checkedAgo(at: number): string { /* … */ }
PieceWhy it's there
PREFIXKeeps BoxHarbor's keys apart from anything else on the same origin.
{ at, value } envelopeEvery save carries its own timestamp, so the reader can judge age and label it.
maxAgeMs on readThe caller decides what counts as stale. Nothing expires on a timer.
Shape checkIgnores a value that isn't an envelope, rather than restoring junk.
try / catch everywhereBlocked storage throws SecurityError; a full store throws QuotaExceededError. Either way the answer is “not saved.”

Both errors are real: MDN lists SecurityError for blocked storage, and MDN lists QuotaExceededError for setItem. Losing a cached page costs nothing, which is why swallowing them is the right call here. It would be the wrong call for user data.

4. The four moves

#MoveWhat goes wrong without it
1Store per tab in sessionStoragelocalStorage would leak one tab's filters into every tab and every visit.
2Stamp, then expire on readHour-old seeder counts shown as if live.
3Read after mountThe server render has no storage, so the HTML and first client render disagree.
4Gate the save until the restore runsThe first render's defaults overwrite what was saved.

Move 1: why sessionStorage

MDN: a page session “survives over page reloads and restores,” “opening a page in a new tab or window creates a new session,” and closing the tab clears it. That matches the goal exactly: pressing Back is the same tab; a new tab is a fresh look.

Move 3: read after mount

Next.js renders client components on the server first. Reading browser storage during render is a listed cause in Next.js's hydration error page, which recommends useEffect instead. So every page restores inside an effect:

useEffect(() => {
  const t = setTimeout(() => {
    const saved = readSession<Saved>(savedKey, 6 * HOUR)?.value;
    if (saved) { setSeason(saved.season); setCache(saved.cache); }
    setRestoredKey(savedKey);   // move 4: now saving may start
  }, 0);
  return () => clearTimeout(t);
}, [savedKey]);

useEffect(() => {
  if (restoredKey === savedKey) writeSession(savedKey, { season, cache });
}, [restoredKey, savedKey, season, cache]);

The setTimeout(0): BoxHarbor runs eslint-plugin-react-hooks 7, whose set-state-in-effect rule flags calling setState synchronously in an effect body. Deferring one tick moves the calls into a callback. The cost is one extra frame showing the defaults before the restore lands.

Move 4: why the gate is a key, not a boolean

Effects run in order on mount. Without the gate, the save effect fires on the very first render, writing the defaults over the saved value before the deferred restore reads it. That's the bug the demo replays.

On the Horizon goes one step further. Its key includes the path and source (horizon:${pathname}:${source}), so the key can change while the component stays mounted, say from Movies to TV. A plain restored = true flag would then let the Movies state save under the TV key before TV's restore ran. Storing which key was restored closes that gap.

5. Predict what the page shows

Write a short reason, then choose. Use the max ages from section 1.

  1. You open a title page, wait for its release table, go elsewhere, then press Back in the same tab 10 minutes later.

  2. You copy the On the Horizon URL from that tab into a brand-new tab.

  3. You reload the search page 2 hours after your last search, same tab.

  4. You reload On the Horizon 2 hours after leaving it on Comedy, page 3, same tab.

  5. The browser is set to block this site from storing data, and you press Back to a page you just left.

Why is the code shaped this way?

  1. Why not read sessionStorage inside the useState initializer, so the first render already has the saved value?

  2. Why does the save effect check restoredKey === savedKey before calling writeSession?

  3. Why is the restore wrapped in setTimeout(() => …, 0) instead of running straight in the effect?

6. Three ways to use one helper

PatternUsed onOn returnSaves when
Snapshot the UI stateOn the Horizon, seasons, catalogPuts every control backAny watched state changes
Show stale, then refreshRelease tableShows saved rows, searches again behind themA fresh result arrives
Restore, refresh on demandSearchShows saved results; you press Search to ask againA fresh result arrives

The release table is the stale-while-revalidate idea, done by hand: “loading cached content right away” while a refresh runs “in a way that doesn't delay the use of the cached response.” If that refresh fails, the saved table stays and its label becomes “couldn't refresh.” A saved table beats an error message.

Search doesn't auto-refresh because re-running it asks every indexer again. The page shows the age and leaves the call to you. A link that asks for a different query skips the restore and searches.

Transfer: pick the pattern

  1. Hypothetical: Image Horse's export dialog should remember the format and quality you picked, per tab.

  2. A dashboard panel takes 8 seconds to load prices that change every few minutes. Refreshing it costs nothing.

  3. A report page runs a query that's billed per run. Users often bounce between it and a detail page.

7. What to keep an eye on

LimitEffect today
5 MiB of session storage per origin (MDN)Big result lists could hit it. Writes then fail quietly and the page starts fresh.
Expired entries are never deletedThey sit in storage until the tab closes. Harmless, but they count toward the 5 MiB.
One search slotOnly the last search is kept, by design.
JSON.stringify round tripOnly plain data survives. A Date comes back as a string; a Map comes back as an empty plain object.
