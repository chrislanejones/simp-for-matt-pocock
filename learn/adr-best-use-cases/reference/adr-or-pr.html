ADR or PR?

Choose the record

Practice heuristics applied to hypothetical Image Horse-style decisions.
ChangeUseful homeReason
Move engine ownership into a workerADR + PRPreserve the boundary choice; explain the implementation in its PR.
Replace a persisted project formatADR + PRCompatibility and migration obligations outlive the patch.
Choose a core library over a viable alternativeADR candidateRecord enduring tradeoffs if they shape the system.
Fix a typo or behavior-preserving renameUsually PRA lasting architectural rationale is unlikely to be missing.
Change one line that alters retention policyADR candidateSmall diff; potentially large data and operational consequences.

Judge architectural significance, not line count. Nygard identifies structure, quality attributes, dependencies, interfaces, and construction techniques as relevant areas. The table applies that guidance; it is not a universal list of triggers. Source: Nygard.

The question to remember

What could a future maintainer accidentally undo because the code does not explain the tradeoff?

A compact practice template

# Decision: [one concrete choice]
Status: Proposed — practice only

## Context
[Constraint or evidence forcing a choice.]

## Decision
[What we propose, and its boundary.]

## Consequences
[Benefit; real cost; follow-up obligation.]

## Alternatives considered
[Credible alternative and why it loses here.]

Context, decision, status, and consequences follow Nygard's basic format. A separate alternatives section is a useful extension for this exercise. Keep unknowns explicit; do not invent measurements or historical reasons. Source: Nygard.

Read the status before following the decision

StatusMeaning in this lesson
ProposedReady to discuss; not yet agreed.
AcceptedAgreed through the project's decision process.
RejectedConsidered and declined; preserve the reason.
SupersededA later accepted record replaces this decision; follow its link.

Preserve accepted decision history when new evidence changes the choice. AWS describes this lifecycle and asks teams to define ownership. Follow the target project's actual conventions. Source: AWS.

Different templates can support the same practice: recording one choice, its rationale, and its tradeoffs. Source: ADR GitHub organization.
