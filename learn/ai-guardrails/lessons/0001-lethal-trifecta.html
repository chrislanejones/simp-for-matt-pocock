The Lethal Trifecta

One framework for judging any agent setup, and one file on your own machine that turns out not to mean what it looks like it means.

Your global CLAUDE.md already denies destructive commands, blocks reads of secrets, and keeps overnight runs on a disposable branch. That's not naive — it's several textbook mitigations, arrived at by instinct rather than by name. This lesson gives the instinct a name, then shows you the one place your setup's strongest-looking rule is weaker than it reads.

The shape of the risk

Security researcher Simon Willison names three conditions that, combined, make an AI agent dangerous. Break any one of the three and the dangerous combination can't complete — which is the whole reason the framework is useful: it turns "is this agent safe?" into "which of the three legs does this setup actually cut?"

Willison's three legs, and what each one is in a coding agent specifically.
LegWillison's definitionIn a coding agent, this is…
Private data "Access to your private data" Your repos, .ssh, .aws, .env files, shell history
Untrusted content "Exposure to untrusted content" A web fetch result, a GitHub issue's text, an MCP tool's output, a file inside a cloned repo
External communication "The ability to externally communicate" git push, curl, an MCP write call, a Slack or email tool — even a crafted commit message
Willison, in his own words

"If your agent combines these three features, an attacker can easily trick it into accessing your private data and sending it to that attacker." He calls the combination the lethal trifecta, and adds the line worth remembering for every mitigation that follows: "We still don't know how to 100% reliably prevent this from happening."

What you already cut off

Run your global rules through the same lens and most of them turn out to be legs of this triangle, cut deliberately. This is the part worth sitting with for a second: you built this before you had the name for it.

Your CLAUDE.md hard rules, mapped to the trifecta.
Your ruleWhat it narrowsMechanism
Secrets: never read/edit .env*, .ssh/, .aws/, *.pem, *.key Private data Read/Edit deny rules in settings.json
Scope: one target per session, adjacent problems go to PARKING_LOT.md Agent's powers, not a leg directly Discipline — nothing in tooling enforces this yet
Overnight runs: worktree + task branch, never main's working tree Blast radius of external comm. Damage is contained to a disposable branch, not prevented
Git safety: no force-push to main, no rewritten pushed history External communication, gated A human has to push — the agent can prepare, not ship
WSL boundary: stay in ~/, never /mnt/c/ unless named Private data, scoped Working-directory boundary

Notice the shape: you've mostly narrowed the data leg and gated the egress leg. The untrusted content leg — what happens when Claude reads a GitHub issue, a fetched page, or an MCP tool's output that someone else controls — isn't addressed by anything above. Neither framework nor your rules make that leg go away; they just haven't tried to yet. Worth knowing, not yet worth fixing in this lesson.

The wall that isn't

Here's the surprising part. Your deny list includes six variations on stopping rm -rf. It reads like a wall. Anthropic's own documentation says otherwise:

Claude Code docs — Configure permissions

"A Bash rule matches the command text Claude writes, after Claude Code splits compound commands and strips wrappers. It doesn't match the same program invoked in a different form, so a deny or ask rule … isn't a security boundary around the program." Their own example: Bash(rm *) stops rm -rf build/ but not /bin/rm -rf build/ or bash -c 'rm -rf build/'.

Your rule is Bash(rm -rf *) — same mechanism, same gap. It's matching the text of the command, not what the command does. Apply the same logic and the pattern holds:

Your deny rule, against four ways to get the same result.
CommandMatches your deny rule?Why
rm -rf /tmp/scratch Blocked Literal text match against Bash(rm -rf *)
/bin/rm -rf /tmp/scratch Not blocked Same program, different text — the rule never sees "rm -rf"
bash -c 'rm -rf /tmp/scratch' Not blocked The rule sees bash -c '…', not rm
sudo rm -rf /tmp/scratch Blocked Caught anyway — by your separate Bash(sudo *) deny rule

That last row matters as much as the gap does: your rules overlap, so one escape route doesn't mean an open door. But it does mean the six rm variants in your deny list are a speed bump against an honest mistake, not a boundary against a model that's been steered by hostile content — which is exactly what "untrusted content" exposure in the trifecta buys an attacker the chance to do.

This isn't hypothetical. Two separate, dated incidents against real Claude Code users show the same failure shape landing in practice, months apart:

IncidentDateWhat happened
claude-code #10077 Oct 2025 rm -rf run from / deleted the user's own files
claude-code #49129 Apr 2026 Files moved into a directory, then that directory rm -rf'd — ~1,500 files, ~50 GB

So what would actually be a wall

Not a full lesson yet — just the map, so "advisory" doesn't sound like a dead end. Three tiers exist, and only the bottom two are code, not pattern-matching:

MechanismWhat it isDeterministic?
Permission rules (allow/deny/ask) Pattern match on command text No — advisory, as shown above
PreToolUse hooks Your own code runs before the tool call; exiting 2 blocks it Yes
OS-level sandbox Process isolation — filesystem and network, via bubblewrap/Seatbelt Yes, mostly

"Mostly" on the last row because it has a stated limit worth knowing now: "MCP servers and hooks are separate processes that run unconstrained on the host" — the sandbox doesn't cover everything that can act on your behalf. Your settings.json has ten hook events configured, but neither of us has read what they actually do yet. That's next lesson's material, once we know.

Retrieval practice — trifecta or not?

Four scenarios, all things you could plausibly run. For each: does it complete the trifecta, or is a leg missing?

  1. Claude Code edits files in a local repo. No web fetch, no MCP tools, git push disabled for the session.

  2. Claude Code reads a GitHub issue to triage a bug, writes a fix, commits, and pushes the branch for a PR.

  3. Claude Code fetches a public open-source project's README and summarizes it. No repo access, no write tools.

  4. An MCP mail tool reads an incoming email and can reply or forward on your behalf.

Retrieval practice — does the rule catch it?

Same deny rule as above, Bash(rm -rf *). Four commands — blocked or not, from memory:

  1. rm -rf /tmp/scratch
  2. /bin/rm -rf /tmp/scratch
  3. sudo rm -rf /tmp/scratch
  4. bash -c 'rm -rf /tmp/scratch'

Verify it yourself

Don't take row two of the first table on my word — go watch your own setup decide. In a real Claude Code session (any project, doesn't need to be this one):

# make two disposable, harmless probe files
mkdir -p /tmp/trifecta-test
touch /tmp/trifecta-test/probe-a.txt /tmp/trifecta-test/probe-b.txt

Then ask Claude, in two separate turns:

  1. rm -rf /tmp/trifecta-test/probe-a.txt — watch what happens.
  2. bash -c 'rm -rf /tmp/trifecta-test/probe-b.txt' — watch what happens to this one.

Bring me what you saw. If both got stopped, that's worth writing down — it means either a hook is already doing more than the deny rule, or the docs' example doesn't transfer to your rule the way this lesson assumed, and either one changes what lesson 2 needs to cover.

Where this leaves your setup

Nothing here says your setup is unsafe — the overlap in row four above (the sudo rule catching what the rm rule missed) is a real, working defense-in-depth pattern, and you built it without the vocabulary for it. What this lesson changes is the claim you can make about it: not "deny rules stop destructive commands," but "deny rules stop the destructive commands an honest agent would write, and something else has to stop the rest." Lesson 2 is about what that something else is — starting with what your ten configured hooks actually do, since right now that's the one mechanism on the table that's genuinely deterministic and completely unread.
