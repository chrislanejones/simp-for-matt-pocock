"If your agent combines these three features, an attacker can easily trick it into accessing your private data and sending it to that attacker." Break any one leg and the chain can't complete. Source.

Enforcement tiers — advisory vs. real

MechanismDeterministic?CoversKnown gap
Permission rules (allow/deny/ask) No Bash command text, file read/write paths Matches literal text, not the program — /bin/rm or bash -c '…' slips past an rm rule
PreToolUse hook, exit 2 Yes Anything you write code to check, before the tool runs Only as good as the check you wrote; separate process from the sandbox
OS-level sandbox (bubblewrap/Seatbelt) Yes, mostly Filesystem writes and network egress for Bash + child processes "MCP servers and hooks are separate processes that run unconstrained on the host"

Rule evaluation order

Deny → Ask → Allow. First match wins; rule specificity doesn't change the order. A deny rule can't carry allowlist exceptions. If a tool is denied at any settings level, no other level can allow it.

SyntaxMeaning
Bash(rm -rf *)Matches command text starting with exactly this, after Claude Code splits compound commands and strips wrappers
Bash(git:*)Equivalent to a trailing space + *
Bash(command:rm *)Not a real form — ignored with a startup warning

Permission modes

ModeScopeSafety net
default (Manual)Read-only until approvedYou, every time
acceptEditsEdits auto-approvedYou, for everything else
autoEverything, with background checksA classifier model — non-deterministic
dontAskOnly pre-approved toolsYour allowlist
bypassPermissions (--dangerously-skip-permissions)EverythingNone — isolated containers/VMs only

Deny rules block in every mode, including bypassPermissions. Allow rules have no effect there. The classifier behind auto mode has a documented bypass: an 80% success rate was demonstrated against it via a crafted archive file.
