What Crosses the Line

Three ways data moves between threads, one way it refuses to — and why that one is the whole story for Image Horse.

You already run a worker. codec.worker.ts works, and it works because the things it sends across are small or already shaped like buffers. The engine is a different animal: its value is a view straight into WASM linear memory, blitted to canvas without a copy. This lesson is about what happens to that view at the thread boundary.

One tangible win by the end: you will be able to look at any payload in useEngineCore.ts and say instantly whether it copies, moves, shares, or throws — and roughly what it costs.

The three doors

There are exactly three ways a value gets from one thread to another, and postMessage picks between them based on what you hand it.

How each door behaves. Cost is on the sending thread.
DoorMechanismCostSender keeps it?
Copy Structured clone ∝ payload size Yes — two independent values
Move Transfer list, 2nd arg O(1) — size-independent No — original is detached, throws on read
Share SharedArrayBuffer O(1), once Yes — same bytes, both threads

Copy is the default and it is not free. Surma benchmarked structured clone across five device/browser combinations and found transfer time correlates tightly with the length of the object's JSON.stringify() output (Surma, Is postMessage slow?). Two numbers came out of it, and they are the numbers to hold:

So copying pixels per stroke is off the table before we start. Which points straight at door two — move it, O(1), done. And that is exactly where Image Horse hits a wall.

The wall

Transfer works by detaching the buffer: the memory is unhooked from the sending realm and rehooked in the receiving one. That is why it is size-independent — nothing is copied, ownership just moves.

WebAssembly linear memory cannot be detached. When the engine creates a WebAssembly.Memory, the spec sets an internal [[ArrayBufferDetachKey]] of "WebAssembly.Memory" on the resulting buffer, and postMessage does not pass that key — so the detach fails (whatwg/html #4601). The engine's heap is not a buffer you may move; it is the running program's memory.

The part that will bite you in review, not in dev

The browsers disagree about the failure. Firefox and Safari throw a TypeError. Chrome has, since 2014, silently copied instead — behaviour that predates WebAssembly and survived because sites depend on it. The spec was amended to throw; Chrome kept shipping the copy.

So the naive port appears to work in Chrome, at full copy cost, and hard-fails the moment anyone opens Safari.

There is a second, quieter trap on the same path. Typed arrays are serializable but not transferable — only the underlying ArrayBuffer is (MDN, Transferable objects). Your flush path deals in Uint8ClampedArray. Putting one in the transfer list is an error; you have to reach through to .buffer, which — for a WASM view — lands you right back at the wall above.

The third door

Sharing sidesteps detachment entirely. A SharedArrayBuffer is cloned, not transferred — both threads end up with their own handle onto the same underlying bytes (MDN, SharedArrayBuffer). And critically for us, new WebAssembly.Memory({ shared: true }) produces a memory whose backing buffer is a SharedArrayBuffer, which means the engine heap itself can be visible from both threads.

That is the door Image Horse most likely walks through. It is not free either:

What the shared-memory door costs.

Baseline-wise it is safe — widely available since December 2021 — with that WebView exception. Hold the question of whether Android WebView matters; it decides an architecture for you, and it is in NOTES.md as an open question.

Retrieval practice

Five payloads, all shaped like things in your codebase. For each: what does postMessage actually do? Answer from memory — scrolling up first will feel better and teach you less.

Copied = structured clone · Passed = ownership transferred, O(1) · Shared = same bytes, both threads · Thrown = TypeError per spec

  1. A pointer event forwarded to the engine worker:

    worker.postMessage({ tool: "stamp", x: 412, y: 260, pressure: 0.8 })

  2. An encoded PNG the codec worker produced, handed onward:

    // png is a Uint8Array over a normal JS ArrayBuffer
worker.postMessage(png, [png.buffer])

  3. The flush path's zero-copy view, sent the obvious way:

    // rgba is a Uint8ClampedArray over stamp_tool's WASM heap
worker.postMessage(rgba, [rgba.buffer])

  4. A full 4096×4096 RGBA layer, no transfer list at all:

    worker.postMessage({ layerId: 3, pixels: rgbaCopy })

  5. A shared-memory engine heap, on a cross-origin-isolated page:

    const mem = new WebAssembly.Memory({ initial: 256, shared: true })
worker.postMessage(mem)

Verify it yourself

Do not take question 3 on my word — the Chrome-copies claim comes from a 2019 spec thread and browsers move. Paste this into the console on any page, in each browser you support:

const m = new WebAssembly.Memory({ initial: 1 });
try {
  // structuredClone uses the same transfer machinery as postMessage
  structuredClone(m.buffer, { transfer: [m.buffer] });
  console.log("copied silently — byteLength still", m.buffer.byteLength);
} catch (e) {
  console.log("threw:", e.constructor.name, e.message);
}

Bring me what each browser said. If Chrome has since started throwing, that is good news worth writing down, and it changes how loudly lesson 2 has to warn about it.

Where this leaves the migration

The obvious plan — keep the canvas on the main thread, run the engine in a worker, post pixels back each flush — is now dead. Copying costs 810× your frame budget; transferring is not permitted; so the pixels cannot make that trip at all. Something else has to move instead.

That is lesson 2: the canvas goes to the worker (transferControlToOffscreen), or the heap goes shared (SharedArrayBuffer), or the engine stays put and only the expensive non-interactive work leaves. Three architectures, and your answer on Android WebView eliminates at least one of them before we start.
